# 05 WP5: templates and project parity (bundled catalog, template deployments, empty project create, several postgres/storage per project)

Contract: `00-contract.md` sections 4 (regions WP5), 5 (`templateDeployments`, `migrateState`), 7 (naming helpers, WP5 signatures, edit points), 9 (WP5 rows), 10. Design source: `designs/wp5.json`, adjusted to decisions 7, 16, 17, 19, 20, 26, 27, 28, 29, 45, 47. Merge position: second (right after WP1); this package lands the structural engine rewrite every later package hooks into, so every hook it calls exists as an identity/no-op in its region until the owner fills it.

## Scope

- Bundle `templates/` and serve `GET /templates`, `GET /templates/:code`, `POST /projects/:id/template-deployments`, `GET /template-deployments/:id` with the cloud's shapes, backed by a port of the platform's pure manifest module and an executor reusing the engine's doors.
- Project create becomes EMPTY (`resources: []`); postgres and storage become multi-instance project services (cap 5 per type, ids `pg-<name>`/`st-<name>`, containers `io-<ref>-pg-<name>`, buckets `io-<ref>-<name>`), registered on the project and materialised on every branch like managed databases; suffixed + canonical-alias env rule extended to `DATABASE_URL` and the S3 bundle; `Branch.bindings` model behind `${{services.x.KEY}}`.
- `GET /projects/:id/services/:sid/credentials`; `DELETE`/`rename` for pg-/st- ids; `?group=` on every database route.
- Lazy state migration of legacy `dbUrl/bucket/s3/storagePublic` into `databases`/`buckets`.
- One dependency: `yaml@^2`.

## Algorithm

### 1. Catalog (`catalog.ts`)

`load()`: for each directory under `cfg.templatesDir` (skip `scripts`, `node_modules`, dot-prefixed) read `insta.template.yaml`; `parseTemplateManifest(text)` lenient (`rejectAuthoredSizing: false`); parse error or `manifest.code !== dirname` -> warn and skip; `draft = raw.meta?.draft === true`; `readme` = `README.md` with the deploy-button paragraph stripped (same matcher as `templates/scripts/publish-lib.mjs findDeployButtons`), null when > 131072 bytes or blank; `logoUrl` = `data:image/svg+xml;base64,...` or `data:image/png;base64,...` from `meta.logo` / `logo.svg` / `logo.png`, null when `meta.logo === 'none'` or missing; `updatedAt` = manifest mtime ISO; `license = upstream.license ?? null`; `documentationUrl = meta.links?.documentation ?? null`; `source = maintainer ?? 'official'`. Cache keyed by the max manifest mtime.

`stats(code)` from `state.templateDeployments`: `deploymentCount`, `totalProjects` (distinct projectId), `successRate` = round(succeeded / concluded * 100) over `succeeded|failed|partial` excluding rows whose error starts with `the daemon restarted`, null when nothing concluded; `live(row)` = succeeded and some `serviceId` still registered with `templateDeploymentId === row.id`; `activeDeploymentCount`, `activeProjects`.

`listTemplates({ query, category })`: non-draft; category exact case-insensitive; query lowercase substring over `code name tagline tags`. `getTemplate(code)`: draft or unknown -> NotFound; `TemplateDetail` with `variables = { required, optional }` from `collectVariables`.

### 2. Manifest module (`manifest.ts`)

Verbatim TypeScript port of the pure half of platform `src/provisioning/templateManifest.ts`: regexes, types, `parseTemplateManifest(input, { rejectAuthoredSizing })`, `collectVariables`, `resolveVariables` (provided -> generate -> default; missing required -> `MissingTemplateVariablesError`), `constraintViolations`, `resolveTemplateString`, `envForService`, `referencedServices`, `envSpecForService`, `generateValue` (`secret:N` -> `randomBytes(N).toString('base64url').slice(0, N)`), `manifestDigest` (sha256 over key-sorted JSON minus `variableOrder`; epoch 2), `parsePlatformRef`, `redactLogTail`, the 4096-byte tail cap. `BadRequestError` becomes `ManifestError` (server maps to 400). `CANONICAL_KEYS` from `manageddb.ts` (postgres `['DATABASE_URL']`, storage the five `AWS_*`/`BUCKET_NAME` keys, managed = catalog bundle keys). YAML via `import YAML from 'yaml'`.

### 3. Registrations (engine)

All registrations below, `provisionBranch` and the renames run inside the engine-wide `serialize('provision')` chain (decision 51), so name and lane reservations are linear across projects.

- `addDbService(projectId, name, opts)`: project or 404; name `/^[a-z0-9][a-z0-9-]{0,38}$/` else 400 `service name must be lower-kebab (a-z, 0-9, -)`; dup -> 409 `service already exists on this branch`; cap `dbServices.length >= cfg.services.maxPerType` -> 400 `branch has reached this plan's limit of <cap> postgres services (INSTA_OSS_MAX_SERVICES_PER_TYPE)` (the cloud's prefix, platform services.ts:684-686, without its dash and upgrade hint); ONE synchronous `mutate` reserves: `assertHostFree(hostFor('postgres', name, ref))` per branch (WP2 hook, no-op until WP2), push the registration `{ id: pg-<name>, name, dataId: randomUUID().slice(0,8), createdAt, status: 'provisioning' }`; then for each branch in creation order `db.provision({ container: pgContainerName(ref, name), network, dataDir: layout().pg(ref, dataId) }, { publishLoopback: cfg.mode === 'local' })` with compensation (`db.destroy` + `data.remove` + drop the registration) on failure; `mutate`: `databases[id] = { url, container, dataId, host }`, status ready; `scheduler.register` per branch (WP3 hook); `router.invalidate()` (WP2 hook: the new lane must listen before `insta db url` is followed by `psql`); emit `service.added {type:'postgres', name}`; row `{ id, type:'postgres', name, status:'ready', pg_version: 16 }`.
- `addStorageService(projectId, name, { public })`: same shape with `storage.provision(ref, network, name)` -> `buckets[id] = { bucket, env, public }`; `setAccess(bucket, network, true)` when public; `router.invalidate()`; row `{ id:'st-<name>', type:'storage', name, status:'ready', public }`.
- `removeDbService`/`removeStorageService` (and the existing `removeComputeService`/`removeManagedService`): a branch-qualified sid strips to the bare id and removal stays project-wide (registrations are project-level; decision 50 counts the teardown across branches); runs under `withOp` for the service's keys on every branch (WP3 hook); per branch destroy the handle (best-effort), `data.remove(pg dir)` (WP4 hook), delete the branch row, drop bindings sourced from it; unregister; `scheduler.forget`; `router.invalidate()`; emit `service.removed`; return `{ teardown: { destroyed, failed } }` counting containers, buckets and directories per branch (decision 50; the route returns it for every type, today's `{}` at server.ts:628 goes away).
- `renameDbService`: grammar + dup; per branch `db.rename(container, pgContainerName(ref, newName))`, rewrite `databases[newId] = { url with host swapped, container: new, dataId, host: hostFor(...) }`; re-key id in `dbServices`, bindings, user secrets (`postgres/<old>` -> `<new>`); `scheduler.rekey`; `router.invalidate`. `renameStorageService`: re-key only (bucket handle immutable); `router.invalidate` (bucket vhost unchanged, alias list may change).
- `addComputeService(projectId, name, volumeGib?, opts)`: as today plus `serviceSettings[cp-<name>] = { alwaysOn: opts.alwaysOn, port: opts.port, templateDeploymentId, templateCode, createdAt }` (fields only when given); `assertHostFree` inside the registration mutate.
- `serviceOf(projectId, sid)`: `parseServiceId(sid)` (strips a `<branchId>:` qualifier first, decision 49) -> check the matching registration list; 404 otherwise. `fixedService()` deleted.
- `resolveSid(projectId, sid, branchQuery?)` (region D helper used by every `/services/:sid/*` route): `sid` of the form `<branchId>:<serviceId>` -> that branch (404 `branch not found` when gone or owned by another project) and the bare serviceId; else `?branch` by name; else the default branch. `qualifiedId(branch, serviceId)`: bare on the default branch, `<branchId>:<serviceId>` elsewhere; `services(projectId, branchName)` rows use it as `id`. Rationale: the CLI takes the id from the branch-scoped list and calls credentials/state/start/stop with NO branch (insta-cli db.ts:241-257, compute.ts:357-370); a bare id would resolve main and `insta db url --branch feat` would print main's DSN.

### 4. Branch provisioning and cloning (`provisionBranch`, `createBranch`; the contract 7.2 skeleton)

`provisionBranch(project, name, isDefault, source, branchId)`: runs under `serialize('provision')` (decision 51); `branchId` is minted by the caller; `docker network create` (a failure whose stderr matches `non-overlapping IPv4 address pool` is rethrown as a 507 `docker has no free network subnets; see docs/self-hosting/install (default-address-pools)`: stock dockerd yields only 31 user-defined networks and every branch is one, 06 §E.4); `ref`; ONE synchronous `mutate`: `assertHostFree` for every label the branch will mint (WP2 hook) and `lanes = this.allocLanes(project, branchId, ids)` (WP2 hook, `{}` until then; writes `state.laneReservations`); for each `dbServices` entry: `dst = { container: pgContainerName(ref, m.name), network, dataDir: layout().pg(ref, m.dataId) }`; `source` null -> `db.provision(dst, { publishLoopback, limits: limitsFor(...) })`, else `db.fork({ ...sourceHandle, url: source.databases[id].url }, dst, { publishLoopback, limits, ensureSourceRunning: () => this.wake(srcKey, { door: 'api' }) })` collecting `{ method, ms }`; then buckets (`storage.provision(ref, network, m.name)` + `setAccess` when public); then managed (`managedDb.provision({ container, network, type, name, password, dataDir: layout().md(...) })`); compensation tears down containers, buckets and directories and `releaseLanes(branchId)`; row `{ id: branchId, projectId, name, isDefault, status:'ready', ref, network, databases (each with its recorded `host`), buckets, managed (each with `host`), lanes, cloneOf, createdAt, apps: {}, dataVersion: 1 }` written in the mutate that also drops the branch's `laneReservations`; `scheduler.register(keys)`; `router.invalidate()`; return the branch and the fork results.

`createProject(name)`: runs inside `serialize('provision')` (decision 51): the name and `refSlug` uniqueness checks and the `s.projects[id]` insert happen in ONE synchronous `mutate` inside the chain (two concurrent creates of the same name or slug cannot both pass the check); registers nothing; `provisionBranch(project, 'main', true, null, randomUUID())` (same chain, re-entered); compensation deletes the project row; emit `project.created`; the route returns `resources: []`.

`createBranch(projectId, name, from)`: `branchId = randomUUID()` FIRST (so the new branch's ServiceKeys `${branchId}:${serviceId}` exist before any op); `withOp(keysOf(source) ∪ keysOf(new, branchId))` (WP3 hook: the per-key operation lock of decision 52, re-entrant, so the nested `deployLocked` calls below and the fork's `ensureSourceRunning` -> `wake(srcKey)` take no second lock; the scaffold body is today's `serialize()` per key); `provisionBranch(project, name, false, source, branchId)`; `volumes = await this.forkVolumes(project, source, target)` (WP4 hook, `[]` until then); for each bucket `storage.cloneInto(source.buckets[id].bucket, target.buckets[id].bucket, network)`; redeploy loop `deployAllocatingPort(..., { startAsleep: this.startAsleepFor(project, target, group) })` (WP3 hook: `false` until WP3, then `!effectiveAlwaysOn(...)`); copy `bindings` and branch-scoped user secrets; `dbVolumeGib`; `await this.sleepNewBranch(project, target)` (WP3 hook); emit `branch.created { from, db: { method, ms }, volumes }`.

`deployLocked`: the argument object per contract 7.2 with `envVars: this.containerize(this.envFor(project, b, group))`; every hook an identity until its owner fills it; record `url`, `host`; `afterDeploy`; `router.invalidate()`.

### 5. Env assembly

`envFor(project, branch, group)` (precedence low to high): `dbSecretsFor` (each `dbServices` entry in creation order: `DATABASE_URL_<SUFFIX>` = lane-form URL; the oldest also `DATABASE_URL`), `storageSecretsFor` (each bucket's env suffixed; the oldest unsuffixed), `managedSecretsFor` (as today with `bundle(laneHost, lanePort, pw, tls)`), user secrets (project-wide, branch-unbound, bound to this group), `bindingsFor(branch, group)` (`envName = credentials(source)[sourceName]`; bindings bypass `isReservedSecret` by design). `secrets(projectId, branch)` = minted + user secrets (no bindings; they are per target). `credentials(projectId, sid, branch)` = the canonical bundle of one service (postgres `{DATABASE_URL}` lane form; storage 5 keys; managed bundle; compute `{}`). Lane rewriting is WP2's `laneAddress`; until WP2 lands the stored container-host URL is returned unchanged.

### 6. Per-service database routes

`dbTarget(projectId, branchName?, group?)`: `group` -> by name or 404 `postgres service not found: <group>`; exactly one -> it; none -> 404 `no postgres service in this project (add one with \`insta services add postgres <name>\`)`; several -> 400 `multiple postgres services - specify one: a, b`. Every `db*` method takes `group` from `?group=`; `dbInstance` returns `id: sid`, `name`, `host`/`port` (WP2 lane), `routeKey`; `runtimeHealth` one row per `dbServices` entry; `observedContainers('db', group?)` the matching containers; `detail()` one `{kind:'postgres', name, ref:{url}}` per database and one `{kind:'storage', name, ref:{bucket}}` per bucket.

### 7. `POST /projects/:id/template-deployments` (accept, synchronous)

A1 project or 404; `deploymentId` must be a UUID. A2 `retrying` when the id exists on this project. A3 manifest: inline `manifest` (YAML text or object; `rejectAuthoredSizing: !retrying`) or `templateCode ?? code` from the catalog (404 `template not found: <code>`; version mismatch 404 `template version not found: <code>@<v> (the registry serves <served>)`). A4 executable: `build:` -> 400; `type: worker` -> 400 (platform wording). A5 ids, digest, claimToken. A6 identity: existing row of another project -> 404; different code/version/digest -> 409 identity message; `succeeded` or `running` updated < 10 min ago -> 202 echo. A7 gates in order `service.add`, `secrets.write`, `deploy`, plus `service.upgrade` when any service declares `volume: true`; the first refusal has replied. A8 branch: existing row's branch (404 if gone); `branchId`; `branch` by name (404); else fresh `<code>`, `<code>-2` .. `-9` (409 when exhausted) via `await engine.createBranch(project.id, name, defaultBranch.name)`. A9 variables: recover stored values/generators from user secrets bound to `compute/<serviceName>` on a retry; `resolveVariables` -> 400 `{error:'missing_variables', missing}`; `constraintViolations` -> 400. A10 initial spec per service (`type`, `image`, `port ?? 8080`, `healthcheck`, `volumeGib: cfg.templates.volumeGib` when `volume`, `alwaysOn`, `state:'pending'`). A11 names: keep recorded; else ladder `''`, `-2` .. `-9` against `compute/<g>` and `postgres/<n>` registrations; too long -> 409; exhausted -> 409. A12 quota per type against `cfg.services.maxPerType` -> 400. A13 insert/replace the record (`status running`, `step create_services`, `claimToken`), emit `template.deploy`. A14 start `run()` in the background; reply 202 `{ deploymentId, deployment: view(record) }`.

### 8. Background run

R1 `create_services`: per manifest service reuse by `serviceId` (`entry.serviceId` stores the BARE id from the registration row `addComputeService`/`addDbService` returns, never a `services()` row id, which is branch-qualified off the default branch, decision 49), else by `(type, name)` only when `templateDeploymentId === deployment.id` (else finish failed with the platform's claimed message), else create: compute `addComputeService(name, volumeGib, { alwaysOn (only when declared), port, templateDeploymentId, templateCode })`; postgres `addDbService(name, { templateDeploymentId })`; `state 'created'`; save. R2 `write_variables`: generators (recovered or generated); `serviceRefs[key] = { url: engine.serviceUrl(project, branch, serviceName), host }` for non-postgres (WP2 seam; until then `apps[group]?.url` or throw `compute service '<name>' cannot expose a URL before deploy`); per non-postgres service `envForService` -> `setUserSecret(projectId, k, v, branch.name, 'compute/<serviceName>')` (unset stale names; a `service` argument is added to `unsetUserSecret`), platform refs -> `setBinding({ envName, target, source: '<type>/<name>', sourceName })`; `entry.env = envSpecForService`; save. R3 `deploy`: postgres entries `healthy` once the container runs (poll up to the health timeout); compute entries `engine.deploy(projectId, branch.name, { image, port, group })` in manifest order; failure -> capture log tail (`runtimeLogs` 40 lines, redacted with every written secret) and finish `partial|failed`. R4 `health_check`: per compute entry: machine up (`liveState === 'running'`; `exited` against running intent -> crashed); no healthcheck -> healthy; `target = new URL(healthcheck, url)` same origin else refuse; `httpProbe` (injectable; default = `http.request({ host: '127.0.0.1', port: cfg.port, path: target.pathname + target.search, headers: { Host: target.host, 'X-Forwarded-Proto': target.protocol === 'https:' ? 'https' : 'http' } })`, 5 s, no redirect follow) 2xx/401/403 = healthy; deadline `cfg.templates.healthTimeoutMs`, poll `healthPollMs`; failures -> `partial|failed` with reasons and the tail. The probe loops back into the router's HTTP lane on the daemon's own port with the service Host (decision 58): it never resolves the public name (which on a NAT'd or sslip.io box may not point back at the daemon) and never touches TLS (with `INSTA_OSS_TLS=internal` Node would reject Caddy's internal CA and every deploy would fail at `health_check`). R5 catch: `partial` when anything deployed, else `failed`. `finish` writes status/error/logsTail and emits `template.deploy.succeeded|failed`. `abandonStale()` at boot: every `running` row -> `failed` with `the daemon restarted while the template deployment was running - retry with the same deploymentId to resume`. `view(row)` per the TemplateDeployment schema; `GET /template-deployments/:id` looks up globally, 404 when absent. The health probe goes through the router's HTTP lane (stamps activity), which is correct.

### 9. State migration (`state.ts` region WP5, pure)

`migrateState(s)`: every project with a branch and no `dbServices` gets `dbServices = [{ id:'pg-db', name:'db', dataId:'db', createdAt: project.createdAt }]` and `storageServices = [{ id:'st-store', name:'store', createdAt, public: <default branch storagePublic> }]`; every branch lacking `databases`/`buckets` gets `databases['pg-db'] = { url: b.dbUrl, container: `io-${ref}-pg`, dataId: 'db' }` and `buckets['st-store'] = { bucket: b.bucket, env: b.s3, public: b.storagePublic ?? false }`. Legacy fields are left in place and never read again. `migrateLegacyContainers()` (main.ts region WP5): best-effort `docker rename io-<ref>-pg io-<ref>-pg-db` and URL host rewrite for branches whose `databases['pg-db'].container === 'io-<ref>-pg'`; a no-op after WP4's data migration renamed them.

## Docs facts for WP8

- `insta project create` starts empty, like the cloud; add services with `insta services add postgres|storage|compute|redis|mysql|mongodb <name>`; up to 5 per type (`INSTA_OSS_MAX_SERVICES_PER_TYPE`); each postgres is its own container, each storage its own bucket; rename and remove work for every type.
- Ids `pg-<name>`, `st-<name>`, `cp-<group>`; the oldest service of a type holds the canonical env alias (`DATABASE_URL`, `BUCKET_NAME`, ...), every service also has suffixed names (`DATABASE_URL_ANALYTICS`).
- `insta template list|info|deploy` work offline from the bundled `templates/` directory through the cloud's routes; deploy supports a registry code, a local directory and a GitHub URL exactly as on the cloud; image services only; `logoUrl` is a data URI; stats are per daemon.
- `insta db url|connect [--group <name>] [--branch <b>]`; with several postgres services the group is required; `--branch feat` returns feat's own DSN (the daemon hands the CLI a branch-qualified service id for non-default branches).
- Removing a service prints the cloud's teardown summary (`destroyed`/`failed` counts across branches).
- Buckets accept path-style and virtual-hosted requests on `AWS_ENDPOINT_URL_S3` (`s3.<domain>` and `<bucket>.s3.<domain>`).
- Template deploys are gated `service.add`, `secrets.write`, `deploy` (and `service.upgrade` when the manifest declares a volume): up to four approvals on a policy of `approve`.
- The `yaml` package is the only new runtime dependency.
