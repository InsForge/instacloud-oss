Everything the console and CLI do runs over the [REST API](/reference/api/overview), so a platform can do it too: provision infrastructure for its own customers, from its own backend, and never show them an InstaCloud screen. Your product on top, InstaCloud underneath.

The API is directly available: [mint a token](/reference/api/overview#minting-a-token) on any account and start building. When you are ready to put a real fleet on it, [contact us](#enterprise-plans) for an Enterprise plan with custom restrictions.

## The recommended setup

Your backend keeps one **master token**: an organization token, minted once (`insta tokens create master --org <orgId>`). It is the credential that creates projects and [mints narrower tokens](/reference/api/overview#minting-a-token), never wider than itself, and it never leaves your backend. From there, two shapes work: **a project per customer**, or one project where **every customer is an app**.

In doubt, take a project per customer. It is the shape the platform's isolation, metering, governance and offboarding are built around, and idle tenants stay cheap: a customer's [Postgres suspends by default](/postgres/overview) and bills only for storage, and their compute can [scale to zero](/compute/overview) the same way. Reserve an app per customer for fleets of small, uniform tenants where sharing one database is a feature, not a compromise.

## A project per customer

When a customer signs up, the master token creates a project for them and mints a **project token** bound to it. Everything that runs for that customer runs under that token:

```bash
API=https://api.instacloud.com

# 1. A project for the new customer. Master token only.
PROJECT=$(curl -s -X POST $API/orgs/$ORG/projects \
  -H "Authorization: Bearer $MASTER" -H "Content-Type: application/json" \
  -d '{"name":"acme"}' | jq -r .project.id)

# 2. A token bound to that project alone. The plaintext is returned once;
#    store it with the customer record.
TOKEN=$(curl -s -X POST $API/tokens \
  -H "Authorization: Bearer $MASTER" -H "Content-Type: application/json" \
  -d "{\"name\":\"acme\",\"orgId\":\"$ORG\",\"projectId\":\"$PROJECT\"}" | jq -r .token)

# 3. Everything for this customer now runs under $TOKEN.
curl -s -X POST $API/projects/$PROJECT/services -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{"type":"postgres","name":"db"}'
curl -s -X POST $API/projects/$PROJECT/services -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{"type":"compute","name":"app","port":3000}'

# 4. Wire the database in, then deploy.
curl -s -X PUT $API/projects/$PROJECT/secret-bindings/DATABASE_URL \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"target":"compute/app","source":"postgres/db"}'
curl -s -X POST $API/projects/$PROJECT/deploy -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"image":"ghcr.io/you/tenant-app:1.0.0","group":"app","port":3000}'
```

The project token is the isolation boundary, so hand it to the customer's runtime without worry: it reaches its own project only (any endpoint outside the binding answers `403 token_scope`), it cannot mint tokens, and a `"access":"read_only"` sibling serves customer-facing dashboards. Each customer gets their own branches for previews and agent runs ([branch per task](/agents/branch-per-task)), `GET /projects/{projectId}/usage` is that customer's bill, and offboarding is two calls: `DELETE /projects/{projectId}` and `DELETE /tokens/{tokenId}`.

## An app per customer

When tenants are many, small and uniform, keep one project and make every customer an **app**: a compute service of their own (`POST /projects/{projectId}/services`), wired to the shared database with a secret binding, deployed under its own `group`, and scaled, restarted or stopped without touching the rest. Logs and metrics still read per app (`GET /projects/{projectId}/logs?group=<app>`), and a database per customer inside the shared Postgres keeps separation clean (`POST /projects/{projectId}/database/databases`). Usage is reported for the whole project though, so per-customer billing needs your own accounting, and a growing fleet hits the plan's per-branch service caps first. When a customer outgrows the shared project, promote them to a project of their own.

Either way, the organization's audit stream (`GET /orgs/{orgId}/events/stream`) gives you one timeline of everything every customer's infrastructure did.

## Enterprise plans

Standard plans cap how many services of each type a branch can hold, sized for one team rather than a fleet of tenants, so an app per customer hits the compute cap first and a project per customer eventually meets its own ceilings.
