## Algorithm

### 1. Docs pages (Mintlify mdx; frontmatter title + description; every behaviour claim names the CLI command that shows it)

1.1 `overview.mdx`: What you get (one daemon over Docker serving the cloud's API; same CLI, MCP, skills, URL shape, sleep rules, templates, dashboard; not there: billing, orgs, members, multi-node, backups until a later milestone). Two ways to run (table: mode / where / address / auth / data dir / use it for: server = a VPS, `https://api.<domain>` and `https://console.<domain>`, admin + `insta_` tokens, `/var/lib/instacloud`; local = your laptop, `http://127.0.0.1:8080` and `*.localhost` names, none, `~/.insta-oss`). Links to the six pages.

1.2 `install.mdx`: requirements; the one-liner; what the script does (numbered, from plan 06, including the firewall rules it adds under ufw/firewalld, the `/etc/docker/daemon.json` `default-address-pools` it writes on a fresh install and why: stock Docker allows 31 user-defined networks and every branch is one, so without it the 32nd `branch create` answers 507 `docker has no free network subnets`); the two printed lines; what it writes (`/etc/instacloud`, `/var/lib/instacloud`, `.img`, the fstab line with `x-systemd.required-by=docker.service` so Docker waits for the data mount, `daemon.json`); options table (`--domain`, `--email`, `--version`, `--tls acme|internal`, `--data-img-gib`, `--print-firewall`, `--print-daemon-json`, `INSTA_OSS_*` pass-through with a link to the sleep page for idle knobs); reflinks (why, probe, XFS loop image, `xfs_info` check); security posture (Docker socket = root; treat admin password and tokens as root credentials; firewall everything but 80, 443 and the database ports you use, but keep the docker0 -> host rules the installer adds or apps cannot reach their own databases); local mode on a laptop (today's quick start: Docker, Node 22, `git clone`, `npm install`, `npm run build:ui`, `npm run dev`, `export INSTA_API_URL=http://127.0.0.1:8080`, no login, URLs `http://<service>-<project>-<branch>.localhost:8080`, `*.localhost` resolution note: macOS and browsers resolve these names; containers and Linux hosts without systemd-resolved do not, so DSNs use `127.0.0.1:<port>` and the `/etc/hosts` line is the fallback for such Linux hosts).

1.3 `setup.mdx`: first visit `https://console.<domain>/setup`, one admin, scrypt, then signed in; sign in later at `/login`; CLI and agents: Tokens page, the exact `insta login --api-key insta_... --api-url https://api.<domain>` line, `--api-key` verified against `GET /me`, `INSTA_API_URL` alternative, switching back to the cloud (`insta env use prod` or unset); MCP with the same bearer (`PLATFORM_API_URL=https://api.<domain>`); headless setup (three curls: `POST /api/auth/sign-up/email` with a cookie jar, `POST /tokens {name}` with the jar and no Origin header needed, `insta login --api-key`; sign-up refused once an admin exists); what requires auth (everything except `/healthz`, `/api/auth/*`, `/auth/*`, `GET /templates*`, static files and the SPA pages such as `/setup` and `/login`; local mode keeps `user: local`); a lost password: `cd /etc/instacloud && docker compose stop instad && docker compose run --rm instad --reset-admin && docker compose start instad` (refuses while the daemon runs).

1.4 `domains.mdx`: hostname table (compute `web-shop-main.<domain>`, postgres `pg-db-shop-main.<domain>:5432`, redis `redis-cache-shop-main.<domain>:6379`, mongodb `mongodb-...:27017`, mysql `mysql-...:<port>` plaintext per-service port, `api.`, `console.`, `s3.`, `<bucket>.s3.`); ref frozen at creation; labels capped at 63 characters (a long name beside a long project/branch pair is shortened to a prefix plus a 6-character hash, shown as-is by `insta services list`); auto domain and its rate-limit caveat; your own domain (`--domain` at install with A records, or `insta compute set-domain shop.example.com --group web` + CNAME to `api.<domain>` or an A record to the box, `insta compute check-domain shop.example.com` until it prints `serving https://shop.example.com`, `insta compute remove-domain shop.example.com`; issued on first request); TLS (edge issues on demand; `INSTA_OSS_TLS=internal` writes the CA to `/var/lib/instacloud/edge/ca.pem`; trust it with `curl --cacert`, `PGSSLROOTCERT`, `NODE_EXTRA_CA_CERTS`); databases from anywhere (`psql "$(insta db url)"`, `insta db connect`, SNI on 5432 with `sslmode=require`, which needs a client that sends the hostname in the TLS handshake: libpq 14 or newer, JDBC 42.2.x or newer, node-postgres, psycopg 3; older clients get `no SNI in the TLS handshake`; redis and mongo on 6379/27017; MySQL plaintext on its own port); buckets (path-style and virtual-hosted requests both work on `AWS_ENDPOINT_URL_S3`); inside a branch (apps reach databases, `api.<domain>` and `s3.<domain>` through the same names; a sleeping database wakes when the app connects; the daemon injects the names into every container); local mode (`.localhost` on 8080, DSNs use `127.0.0.1:<port>`, no TLS).

1.5 `sleep.mdx`: the promise; what counts as activity (verbatim rules from plan 03); when a service sleeps (five conditions, 30 s cadence, 5 min compute, 10 min databases, so 5 to 5.5 min after the last request; the 10-minute create grace counts from when the service was created, not from the last daemon restart); memory pressure (15 percent floor, LRU, always-on never evicted, a service woken in the last minute or answering a request right now never evicted, disabled on macOS without `INSTA_OSS_MEM_BUDGET_MB`); what sleep does (`docker stop` sends the image's stop signal: SIGTERM for apps and managed databases, SIGINT for the official Postgres image, which is its fast shutdown; apps get the signal through docker's `--init` even behind a shell entrypoint; waits 10 s, 30 s for databases, before SIGKILL; disk survives; 1 to 3 s wake); what wakes (request on any lane held up to 60 s for the wake plus up to 38 s of readiness retries, `insta compute start`, a deploy; `insta compute stop` is durable and traffic never wakes it); always-on and limits (`insta compute always-on on web`, `services add compute --always-on`, manifest `alwaysOn: true` in hermes, n8n, openclaw; `insta db always-on on`; `insta compute limits web --memory 512mb`, the grid, the cap); the divergence (self-host default scale-to-zero, cloud default always-on); tuning table (`INSTA_OSS_IDLE_COMPUTE_SEC`, `INSTA_OSS_IDLE_DB_SEC`, `INSTA_OSS_SWEEP_SEC`, `INSTA_OSS_CREATE_GRACE_SEC`, `INSTA_OSS_STOP_GRACE_SEC`, `INSTA_OSS_STOP_GRACE_DB_SEC`, `INSTA_OSS_WAKE_TIMEOUT_SEC`, `INSTA_OSS_RAM_FLOOR_PCT`, `INSTA_OSS_MEM_BUDGET_MB`, `INSTA_OSS_ALWAYS_ON_DEFAULT`, `INSTA_OSS_SCHEDULER`; set in `instad.env`, then `docker compose up -d`); how it reads (`insta services list` shows `asleep`, `insta compute status` shows `desired=running live=suspended`, the dashboard says Sleeping; `insta events` carries `service.sleep` and `service.wake`); the known edge (a long computation with no inbound traffic sleeps; always-on is the override).

1.6 `branching.mdx`: what a branch is here (container per branch, bucket per branch, keyed by the ref); where the data lives (`pg/<ref>/<id>`, `vol/<ref>/<id>`, `md/`, `garage/`); how a clone works (reflink copy of a source at rest, start, crash-consistent recovery, sub-second at any size, nothing is woken to be cloned; `pg_basebackup` whenever the source is running or the filesystem cannot reflink; `insta events` shows `branch.created` with `db.method` and `volumes`); volumes fork the same way (the cloud gives a branch an empty volume: state the difference); buckets `rclone sync`; managed databases start empty on both; a new branch sleeps until its first request; first boot after an upgrade migrates legacy docker volumes.

1.7 `upgrade.mdx`: re-run the one-liner; pin with `--version`; roll back with the previous version; what a restart does to sleeping services (nothing, and the idle clock starts fresh while the create grace does not); backups until the backups routes ship (`pg_dump "$(insta db url --branch <b>)"`, tar of `vol/`, the Garage dirs; the backups API routes answer 501 with the same hint; there is no `insta backup` command); growing the loop image; local mode upgrade (`git pull`, `npm install`, restart); the daemon keeps the newest 5000 events.

`docs.json`: the Self-hosting group lists overview, install, setup, domains, sleep, branching, upgrade in that order.

### 6. `e2e/local-smoke.sh` (runs on the host)

Inputs: `INSTA_OSS_PORT` (8080), `E2E_RUN_ID`, `E2E_START_DAEMON=1`, `E2E_IMAGE` (`traefik/whoami:v1.10`); idle knobs `INSTA_OSS_IDLE_COMPUTE_SEC=15 INSTA_OSS_IDLE_DB_SEC=20 INSTA_OSS_SWEEP_SEC=2 INSTA_OSS_CREATE_GRACE_SEC=0 INSTA_OSS_RAM_FLOOR_PCT=0` (the ticker stays on because step 7 tests sleep; the RAM floor at 0 disables memory-pressure eviction, which on a 7 GiB runner with images loaded would otherwise stop the containers under test).
0. Preflight: docker, node >= 22, `insta` (else `npm i -g insta@latest`), `psql`, `HAVE_LOCALHOST_DNS` via `getent hosts e2e-probe.localhost`.
1. Daemon: `INSTA_OSS_MODE=local INSTA_OSS_DATA_DIR=$RUNNER_TEMP/insta-oss-$RUN npx tsx src/main.ts > daemon.log 2>&1 &`; trap kills it; `wait_for 90 curl /healthz`.
2. `export INSTA_API_URL=http://127.0.0.1:$PORT`; `insta status` contains `local`.
3. Project `e2e-local-$RUN`: link-and-delete stale; trap teardown; `insta project create`; `insta services list` has no `postgres/` or `storage/`; `services add postgres db`, `services add storage store`, `services add compute web`; `services add postgres analytics` succeeds and `insta db url --group analytics` differs from `insta db url`; duplicate `services add postgres db` exits non-zero.
4. Credentials: `insta secrets --print`; `DATABASE_URL` host is `127.0.0.1` with a port in the lane range; `psql_roundtrip`; `s3_roundtrip` on the printed `AWS_ENDPOINT_URL_S3` (`http://127.0.0.1:3900`).
5. Deploy: `insta deploy --image $E2E_IMAGE --port 80 --group web`; URL matches `^http://web-[a-z0-9-]+\.localhost:[0-9]+/?$`; `ensure_host` when needed; `wait_for 60 curl -sf $URL/` and the body contains `Host: web-` (Host-based routing); `docker port $(svc_container $REF web)` shows only a `127.0.0.1:` mapping.
6. Branch: seed `qa_branch_probe`; `measure insta branch create feat --from main` (soft-assert < 60 s); `insta branch list --json` shows feat; `insta services list --branch feat --json` ids are branch-qualified (`<uuid>:pg-db`) while `--branch main` ids are bare; `insta db url --branch feat` (the CLI follows the list's id into `/credentials` with no branch) differs from `insta db url`; feat sees `from-main`; a write on feat is not on main; feat's app URL `web-<slug>-feat.localhost` answers after hold-and-wake (`wait_for 60`). Volume fork: `services add compute voljob --volume 1`, deploy, `docker exec ... sh -c 'echo forked > /data/marker'`, `branch create feat2`, curl feat2's voljob URL, `docker exec $(svc_container ${SLUG}-feat2 voljob) cat /data/marker` == `forked`. `insta events --json` has `branch.created` and prints `db.method`.
7. Sleep and wake: stop curling; `wait_for 60` until `cstate web` == `exited` and `cstate $(pg_container $REF db)` == `exited` (never `paused`); `insta compute status web` contains `desired=running` and not `live=running`; wake compute with curl (200, then `running`); wake db with `PGCONNECT_TIMEOUT=60 psql "$DBURL" -tAc 'select 1'` == 1; stopped is never woken: `insta compute stop web`, curl -> 503 or refused, still `exited` after 10 s, `insta compute start web`, curl 200; always-on: `insta compute always-on on web`, wait 2 windows + sweep, still `running`, `insta compute always-on off web`; `insta events` contains `service.sleep` and `service.wake`.
8. Limits: `insta compute limits web --memory 512mb`; `docker inspect -f '{{.HostConfig.Memory}}'` == 536870912; read-back shows 512.
9. Templates: `insta template list` contains `n8n` and `hermes`; `insta template info n8n --json` has `upstream.pinned`; `insta template deploy ./e2e/fixtures/tpl-hello --branch main --yes --json` -> `status succeeded` and `services[0].url`; curl 200; `insta services list` shows `compute/hello`; second deploy -> `hello-2` (soft).
10. Dashboard: when `ui/dist` exists, `curl /` contains `<div id="root"` and `window.__INSTA_OSS__`.
11. Teardown (trap): `insta policy set project.delete allow`; `insta project delete`; then assert no `io-$SLUG-` containers or networks and no `$INSTA_OSS_DATA_DIR/pg/$SLUG-main`; kill the daemon. Final line `LOCAL SMOKE PASSED`.

### 7. `e2e/server-smoke.sh` (runs on the runner VM as root)

Inputs: `E2E_RUN_ID`, `INSTA_OSS_IMAGE` (built from the checkout), `INSTA_OSS_DOMAIN` default `127-0-0-1.sslip.io`, `INSTA_OSS_TLS=internal`, the idle knobs including `INSTA_OSS_RAM_FLOOR_PCT=0`.
0. Preflight: root or sudo; 80/443/5432 free; docker; `getent hosts api.$DOMAIN` == 127.0.0.1 else `ensure_host` for every host touched; `xfsprogs`.
1. Install: `sudo env INSTA_OSS_IMAGE=... INSTA_OSS_DOMAIN=... INSTA_OSS_TLS=internal <idle knobs> sh install.sh | tee install.log`; exit 0; log contains `https://console.$DOMAIN/setup` and the upgrade line; `docker ps` shows `io-instad`, `io-edge`, `io-garage`; `findmnt -no FSTYPE /var/lib/instacloud` == `xfs` and `xfs_info | grep reflink=1`; `cp --reflink=always` inside the data dir succeeds; `CA=/var/lib/instacloud/edge/ca.pem` exists (else `INSECURE=1` with a loud line).
2. Health and auth: `wait_for 120 curl --cacert $CA https://api.$DOMAIN/healthz`; `api_code GET /me` without a token == 401; `curl https://console.$DOMAIN/setup` is HTML containing `__INSTA_OSS__`.
3. Admin and token: cookie jar; `POST /api/auth/sign-up/email {"name":"admin","email":"admin@example.test","password":"<random 24>"}` -> 200; second sign-up -> 422; `POST /tokens {"name":"ci"}` with the jar -> 201 and `token` starts with `insta_`; `GET /tokens` lists one record; `export INSTA_TOKEN`.
4. CLI login: `NODE_EXTRA_CA_CERTS=$CA insta login --api-key "$TOKEN" --api-url https://api.$DOMAIN` prints `logged in as admin@example.test`; `insta status` shows the email; `insta login --api-key insta_bogus ...` fails with the `rejected` wording. Export `NODE_EXTRA_CA_CERTS` and `PGSSLROOTCERT=$CA`.
5. Project, services, credentials, deploy: as local steps 3 to 5 with https; URL matches `^https://web-[a-z0-9-]+\.$DOMAIN/?$`; `insta db url` host matches `^pg-db-[a-z0-9-]+\.$DOMAIN$` with port 5432 and `sslmode=require`; `psql_roundtrip` over public 5432 (SNI lane); `s3_roundtrip` against `https://s3.$DOMAIN`.
6. Branch: as local step 6 with a HARD assertion that `branch.created` has `db.method == reflink` and elapsed < 5000 ms after seeding 50 MB.
7. Sleep and wake: as local step 7.
8. Custom domain (guarded): `insta compute set-domain e2e.example.test --group web` -> non-501 (the printed records name `CNAME e2e.example.test -> api.$DOMAIN`); `insta compute check-domain e2e.example.test` prints `cname pending` and `serving not yet` with no `UNCONFIRMED` line (the envelope carries no `ssl` field); `insta compute remove-domain e2e.example.test`.
9. Templates: as local step 9 with https; `api_code GET /templates` without a bearer == 200.
10. Upgrade: re-run the exact install command; exit 0; `wait_for` healthz; `insta project list` still shows the project; the deployed URL answers again after wake; `docker inspect` of the pg container shows a bind mount under `/var/lib/instacloud/pg/`.
11. Teardown: `insta policy set project.delete allow`; `insta project delete`; io- containers gone; stack left running (optional `E2E_UNINSTALL=1` runs `docker compose down -v` and unmounts).

### 8. `.github/workflows/e2e.yml`

Job `local` (pull_request, push to main; ubuntu-latest): checkout, setup-node (`.nvmrc`), `npm ci`, `npm run build:ui`, `npm i -g insta@latest`, `postgresql-client`, pre-pull images, `E2E_START_DAEMON=1 E2E_RUN_ID=<run>-<attempt> sh e2e/local-smoke.sh`; always upload `daemon.log` and `docker ps -a`. Job `server` (push to main, workflow_dispatch, nightly, PRs labelled `e2e-server`): checkout, `docker build -t ghcr.io/insforge/instacloud:ci .`, `postgresql-client xfsprogs`, `npm i -g insta@latest`, `sudo -E env INSTA_OSS_IMAGE=ghcr.io/insforge/instacloud:ci sh e2e/server-smoke.sh`; always upload `install.log`, redacted `instad.env`, `docker compose logs`. Separate VMs, so container names never collide; `concurrency` per job and ref with cancel-in-progress. `ci.yml` (unit + Docker integration) stays its own job.
