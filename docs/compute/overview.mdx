title: "Compute"

A compute service runs your container — web app, API, worker — in an isolated microVM with its own URL. Production stays warm, branch services sleep when idle, and billing is actual usage either way.

```bash
insta services add compute app
insta deploy .
```

## What a compute service is

An image, its environment, and a listen port:

- **Image** — built remotely from your Dockerfile on `insta deploy .`, or supplied prebuilt with `--image`. See [build & deploy](/deploy/overview).
- **Environment** — user secrets plus explicitly bound provider credentials, injected at deploy time. The [quickstart](/quickstart) shows the binding step.
- **Port** — an explicit `--port` wins; otherwise the Dockerfile's last `EXPOSE` line; otherwise 8080.

A branch can run several compute services, each its own group with its own URL and deploys. WebSocket apps deploy with `--websocket` for a larger guest and connection-based concurrency.

## MicroVMs

Each service runs in its own microVM — hardware-level isolation rather than a shared-kernel container, which is what makes it safe to run agent-built code next to everything else. Need disk that survives restarts? Attach a persistent `/data` volume:

```bash
insta services add compute app --volume 1
insta compute volume app --size 10
```

Any plan can attach the default 1 Gi; larger sizes are paid and plan-capped. Volume-backed services stop (cold wake) instead of suspending, so the disk stays consistent.

## Lifecycle

Compute on your default branch is always-on. On every other branch it scales to zero, and an idle machine suspends until the next request wakes it in seconds. Control the lifecycle directly:

```bash
insta compute status    # desired vs actual state
insta compute start
insta compute stop
insta compute suspend
```

`insta compute always-on on|off` overrides that on any branch, and `--no-always-on` at creation starts a service scale-to-zero. Billing is actual usage either way, so an always-on machine bills continuously while a sleeping one costs almost nothing. Scale-to-zero also stops any background work running in the container, which [limitations](/limitations/overview) covers. Machine counts and specs move with `insta services scale` and `insta services upgrade` on paid plans. Custom domains attach per branch with `insta compute set-domain`.

<Note>
On self-hosted InstaCloud OSS, `services scale`/`upgrade` are cloud-only, while `--always-on` and custom domains work as they do here. `insta secrets bind` answers `501`: every compute container already receives each service's credentials under their own names, so read those (`insta secrets list` names them) or set your own with `insta secrets set`. The command-by-command list is in [COMPATIBILITY.md](https://github.com/InsForge/instacloud-oss/blob/main/COMPATIBILITY.md).
</Note>
