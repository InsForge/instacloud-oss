## Upgrade

Re-run the one-liner. The script sees the existing `/etc/instacloud/instad.env`, keeps every
setting in it, and recreates only what changed:

```bash
curl -fsSL https://raw.githubusercontent.com/InsForge/instacloud-oss/main/install.sh | sh
```

Pin a version, or go back to one:

```bash
curl -fsSL https://raw.githubusercontent.com/InsForge/instacloud-oss/main/install.sh | sh -s -- --version v0.1.0
```

Branch containers are not part of the compose stack, so they are not recreated and keep running
through the upgrade. The port check is skipped while the stack is up.

## What a restart does to sleeping services

Nothing. A sleeping service is a stopped container with its files on disk, and it stays that way
until something asks for it. Two details:

- the idle clock starts fresh, so nothing is swept for one full window after the restart
- the create grace does not restart, because it counts from when the service row was created

## Backups

The backups API routes answer `501` today, with a hint to `pg_dump` the database, and there is no
`insta backup` command, so this procedure is the only one there is. Follow it exactly: the parts
that look optional are the parts that decide whether the archive is worth anything.

**What holds state.** Everything is under the data directory (`/var/lib/instacloud` by default):

| path | what is in it | who writes it |
| --- | --- | --- |
| `state.json` | every project, branch, service, secret and event | the daemon |
| `pg/` | each Postgres service's data directory | its own container |
| `md/` | each **redis, mysql and mongodb** service's data | its own container |
| `vol/` | each compute group's `/data` volume | your app's container |
| `garage/` | the object store's metadata and objects | the `io-garage` container |
| `edge/`, `caddy/` | the internal CA and issued certificates | the `io-edge` container |

`md/` is the one an earlier version of this page left out, and a backup that omits it loses every
managed database while appearing to succeed. `metrics-history.json`, the dashboard's three days of
chart history, is left out on purpose: it is disposable and refills from live samples.

**The databases**, one dump per Postgres service per branch, which is the copy you should trust.
With one Postgres on a branch, `insta db url` finds it; with several it refuses to guess, so name
each one with `--group`. Every file below holds a whole database or the box's secrets, so they all go
into one directory only you can read, whatever mode an older file of the same name had:

```bash
(
set -eu                                               # any failure stops the block
umask 077
B=backup-$(date +%Y%m%d-%H%M%S)
mkdir -m 700 "$B"                                     # refuses a directory that already exists
u=$(insta db url); pg_dump "$u" > "$B/main.sql"                              # the branch's only Postgres
u=$(insta db url --branch feat); pg_dump "$u" > "$B/feat.sql"
u=$(insta db url --group db --branch main); pg_dump "$u" > "$B/main-db.sql" # one line per service when there are several
u=$(insta db url --group analytics --branch main); pg_dump "$u" > "$B/main-analytics.sql"
sudo cp /etc/instacloud/instad.env "$B/instad.env"    # INSTA_OSS_SECRET and every setting, not in the archive
cert=$(sudo sed -n 's/^INSTA_OSS_TLS_CERT_FILE=//p' /etc/instacloud/instad.env)
key=$(sudo sed -n 's/^INSTA_OSS_TLS_KEY_FILE=//p' /etc/instacloud/instad.env)
[ -z "$cert" ] || sudo cp -L "$cert" "$B/tls-cert.pem" # --tls custom: the pair lives outside the data directory
[ -z "$key" ] || sudo cp -L "$key" "$B/tls-key.pem"
echo "backup written to $B"
)
```

`insta services list` names the Postgres services on the current branch.

**Everything else.** Stop EVERY writer first, not just the daemon: the branch containers and the
object store keep writing to `md/`, `vol/` and `garage/` while `tar` reads them, and an archive
taken over a running container is torn for that service even when the file list is right.

```bash
(
set -eu                                               # a failed tar never replaces the last good archive
cd /etc/instacloud
umask 077                                             # the archive holds credentials and certificates
docker compose stop                                   # instad, the edge AND garage
trap 'rm -f instacloud-data.tgz.tmp; docker compose start' EXIT   # the stack comes back whatever happens
docker ps -q --filter 'name=^io-' | xargs -r docker stop   # every branch container
rm -f instacloud-data.tgz.tmp                         # a fresh file, so umask applies
tar -C /var/lib/instacloud -czf instacloud-data.tgz.tmp state.json pg md vol garage edge caddy
chmod 600 instacloud-data.tgz.tmp                     # private even over an older archive
mv instacloud-data.tgz.tmp instacloud-data.tgz
)
insta compute start <group>                           # per group you had running, or let traffic wake them
```

The paths assume the default data directory; with `--data-dir` use yours (`INSTA_OSS_DATA_DIR` in
`/etc/instacloud/instad.env`). Treat the archive like a credential: it carries every service's credentials, data and
issued certificates (`instad.env` and a custom TLS pair are copied into the dump directory above), so encrypt any copy that leaves the box.

The `docker ps` line is the one people skip. Branch containers are not part of the compose stack, so
`docker compose stop` does not touch them; the filter matches every container this daemon owns,
because they are all named `io-<ref>-…`. Services that were asleep stay asleep and cost nothing.

**What the archive is and is not.** With every writer stopped it is a consistent point-in-time
copy of the roots it lists. If you cannot stop the branch containers (you have traffic to serve), the
archive is still consistent for `state.json` and for any service that was ASLEEP at the time, and
NOT for a service that was running: for those, use the `pg_dump` above for Postgres, and accept
that a running Redis, MySQL or MongoDB is captured mid-write. There is no third option today.

**Restore.** Restoring from the archive is not supported yet
([#139](https://github.com/InsForge/instacloud-oss/issues/139)). The archive carries `state.json`
and the data, but not the Docker containers and networks `state.json` points at, and a wake does
not recreate a missing container: it fails instead. That holds on a new machine, and on this one
for any service, branch or project deleted since the backup. Keep the archive as a cold copy.

The supported recovery is the dumps. Recreate the project and its services with `insta`, then load
each Postgres dump into its service:

```bash
insta project create demo
insta services add postgres db
psql "$(insta db url --group db)" < backup-<stamp>/main-db.sql       # one line per Postgres service per branch
```

Redis, MySQL, MongoDB and bucket contents do not come back this way; export them with their own
tools too.

## Growing the data disk

When the installer created a loop image and it is filling up:

```bash
truncate -s +20G /var/lib/instacloud.img
losetup -c "$(findmnt -no SOURCE /var/lib/instacloud)"
xfs_growfs /var/lib/instacloud
```

No downtime, and nothing to restart.

## Local mode

```bash
git pull
npm install
npm run build:ui
npm run dev
```

State stays in `~/.insta-oss`.

## Events

The daemon keeps the newest 5000 events and drops older ones, so treat `insta events` as a recent
timeline rather than an archive. Anything you want to keep, export.
