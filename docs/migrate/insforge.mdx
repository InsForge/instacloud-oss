This guide is for an InsForge you host yourself, the four containers `docker compose` brings up. On InstaCloud two of them run unchanged as **compute** services, its Postgres becomes a **postgres** service, and its files move to a **storage** service. Your app keeps its keys, your users keep their sessions, and only the `baseUrl` in your code changes. Your coding agent does most of it.

InstaCloud offers:

- **Postgres with real branching.** A branch opens as a copy-on-write clone holding all of the parent's data, at its own connection string, so a feature or an agent task can run migrations nowhere near production.
- **Built for coding agents.** A CLI and an MCP server your agent drives directly, with an approval gate on the actions that matter.
- **Flexible deployments.** A local directory, a GitHub repo, or an image from any registry.
- **Managed services alongside.** Postgres, Redis, MySQL, MongoDB, and object storage in one project.
- **Real support.** An active community on [Discord](https://discord.com/invite/MPxwj5xVvW).

## Migration steps

We will migrate an InsForge started with the [Docker guide](https://github.com/InsForge/InsForge/blob/main/deploy/docker-deploy.md): `deploy/setup.sh`, then `docker compose up -d`. Its `.env` holds what matters:

```ini
JWT_SECRET=...
ENCRYPTION_KEY=...
ACCESS_API_KEY=ik_...
ACCESS_ANON_KEY=anon_...
POSTGRES_DB=insforge
```


**Edge functions do not migrate yet.** If your app calls them, wait for this guide to grow that step. Everything else comes over.

**Keep your keys.** Your agent carries `JWT_SECRET`, `ENCRYPTION_KEY`, `ACCESS_API_KEY` and `ACCESS_ANON_KEY` over unchanged, which is what keeps your users logged in and your stored secrets readable. Fresh ones would log everyone out.

### 1. Point a coding agent at your InsForge

Work in the directory `setup.sh` created: its `.env` and `deploy/` folder are what the migration reads. Give your agent the skill there:

```bash
cd ~/insforge
npx -y insta@latest setup agent
```

That installs the `insta` CLI, the `insta` skill, and the MCP server for every coding agent on this machine. The skill is what knows how an InsForge stack maps onto services here.

### 2. Create a project

```bash
insta project create insforge
```

Or click **Create Project** in the [console](https://console.instacloud.com). A new project starts empty.

{/* screenshot: console, Create Project */}

### 3. Ask your agent to migrate

Stop everything that writes, and leave Postgres running for the copy:

```bash
docker compose stop insforge postgrest deno
```

Files and database are two halves of one state, and nothing may write to either while they are copied. If InsForge runs on another machine, bring its `.env`, `deploy/` folder and `storage-data` volume here first. Then hand over:

```text title="Prompt" wrap
Migrate my self-hosted InsForge in ~/insforge to InstaCloud: the database, its users and the storage files. Keep the secrets from its .env. Follow the insta skill's migration runbook, and stop before I switch my app over.
```

It will ask you to approve anything that touches production, and it moves the files before the database, because the list of files lives in the database.

{/* screenshot: console, project with two compute services, a postgres service and a storage service */}

### 4. Switch your app over

```text title="Prompt" wrap
Give me the new InsForge URL, and confirm the anon key and API key match the ones in my .env without printing either value.
```

Change `baseUrl` in your `createClient` call to that URL. Unless your app calls edge functions, nothing else in it changes. Leave the old stack stopped rather than deleted, so you can go back to it.

## Cron jobs

Cron jobs are not supported for now. InsForge schedules are not affected: they run in `pg_cron` inside your database and came over with the dump.

And that is it. Every InstaCloud action your agent took is a command you can run yourself, in the [CLI reference](/reference/cli/overview). The inspection on the other side used `docker compose` and `pg_dump`.

Once you are settled in, [database branching](/postgres/branching) is the part most people came for: one command clones your database, storage and apps, data included, so work an agent does *on its branch* stays there. The branch boundary is separation, not authorization: any command taking `--branch` still reaches `main`, so set policy for the actions that matter. Stuck anywhere?
